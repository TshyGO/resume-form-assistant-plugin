# 邮件来源接口（#353）

本任务提供官方 API 接入所需的共用边界，用模拟 Graph / Gmail 来源验收。
微软 OAuth、Graph HTTP 请求和 Gmail HTTP 请求分别属于 #354、#355、#360；本任务完成不代表这些邮箱已可通过官方 API 连接。

## 审核时先看这些

本次基于现有 QQ / 163 流程，让不同邮箱交出相同格式的邮件摘要，共用后面的处理：

`邮箱提供摘要 → 筛选 → 待确认 → 保存或忽略 → 确认后下载完整邮件 → 入档`

各邮箱只需负责“继续检查邮件”和“下载这封完整邮件”两件事；账号与邮件编号仍由各来源分别管理。
QQ / 163 的实际取信方式和当前界面保持原有操作，本轮用模拟 Outlook / Gmail 数据验证新接口。

| 场景 | 已验证的结果 |
| --- | --- |
| 扫描找到面试邀请 | 显示待确认和筛选原因，此时不下载正文 |
| 用户忽略后重新扫描 | 同一封邮件保持忽略 |
| 邮件已经手动导入 | 确认时识别重复，跳过下载 |
| 第 2 页检查失败后重启 | 从第 1 页末的已保存位置续查，不跳过第 2 页 |
| 本机保存候选失败 | 候选和下一位置同时回滚 |
| 网络请求一直没有返回时取消 | 停止等待；候选和检查进度不误更新 |
| 保存邮件时失败 | 保留待确认记录，可以重试；已入档原件不会重复新增 |
| 下载期间恢复档案 | 拒绝旧任务写入恢复后的档案 |

## 原有模型和问题

#331 的账号、候选、忽略记录、文件夹 UID 游标与信头重试保存在数据根目录的 `mailboxes.sqlite`。
密码通过本机账号 ID 对应的 `mailbox:{id}` 保存在系统凭据库，SQLite 不存密码。
已确认邮件仍由现有证据导入流程写入档案，候选与位置不属于档案备份。

原来账号必须拥有 IMAP 连接配置，候选必须拥有文件夹、UIDVALIDITY 和 UID。
这不适合 Graph / Gmail 的邮件资源 ID 和分页、增量位置。
邮箱地址原来还承担 IMAP 账号的唯一约束，不能拿这个约束推断两个官方账号或邮箱别名属于同一身份。

## 最小边界

- `Account.id`：本机账号 ID，继续用于凭据库和候选归属。
- `Account.source` 与 `sourceAccountId`：连接器种类和服务商认证返回的稳定账号身份。服务商 ID 应包含其必要的租户/身份命名空间；不可直接用邮箱别名代替。
- `Candidate.locator`：IMAP 使用文件夹、UIDVALIDITY、UID；API 使用来源种类和不透明邮件资源 ID。只用于定位原件。
- `Header` 的指纹和档案 `MailKey`：仍按已有 Message-ID、发件人、时间及无 ID 的回退规则处理重复邮件，不把 API 资源 ID 当 RFC Message-ID。
- `Position`：IMAP 游标与 API 位置显式区分。API 字符串由来源解释，可以包含分页继续位置、增量位置或恢复所需的组合状态。不能保存 OAuth 令牌、凭据或会话信息。

IMAP 继续使用原有只读扫描器、文件夹恢复和持久化信头重试，扫描结果接入共用的 `persist_source_page` / `Database::commit_metadata`。
`MimeSource` 统一确认下载，绑定已认证的本机账号和来源种类；IMAP 由 `ImapSource` 适配现有下载器。
`PagedSource` 为 API 扩展元数据分页，`scan_api_page` 提供网络读取与本机提交之间的接入点。这里刻意保留 IMAP 已工作的 UID 扫描流程。

## 接入约束

1. 来源在认证后调用 `save_api_account`。同来源、同服务商稳定身份重新授权保留本机账号 ID；相同地址但不同服务商身份不会合并。IMAP 同地址更新保持原行为。
2. API 扫描接入既有邮箱调度和互斥门；每页从 `source_position` 读取已持久化状态，交给 `read_metadata`，再在短档案锁内调用共用提交。来源不能依靠内存里已前进的位置恢复。
3. 元数据页只带信头与来源定位，不带正文、预览、附件或 MIME。具体 API 适配器必须显式选择元数据字段，不得默认下载正文。每页最多 100 封，每封序列化信头最多 64 KiB；网络元数据请求有 30 秒上限。
4. 共用流程执行本地筛选、已入档去重，在同一 SQLite 事务写入候选和下一位置。未命中不留信头；空页仍可以保存位置。任一步失败都不推进持久化位置。
5. 忽略与已导入状态不因重扫、文件夹/标签变化或来源 ID 更新而重置。候选/忽略/位置按档案 ID 隔离，账号删除继续级联清理。
6. 确认前再次检查档案中是否已有同一邮件，已有则不下载。否则通过 `confirm_from_source` 下载原始 MIME；实现必须流式限制 25 MiB 并设置读取超时，不应先把无限响应读入内存。共用边界再次验证大小和信头身份。
7. 网络不持有档案/恢复锁。扫描提交与确认入档均校验档案 ID、恢复 epoch、账号连接/稳定身份；取消会唤醒正在等待的请求并丢弃该次操作，已取消的结果不提交。来源须重建被中断的传输连接后再重试。来源类型或账号不匹配时在网络前拒绝。
8. 确认下载/保存失败保留候选。若档案写入成功、候选完成标记失败，重试沿用现有 Message-ID/原件摘要去重，不重复创建证据。
9. 来源只能返回安全错误类别。不得把响应文本、密钥、令牌、正文、会话或完整分页 URL 记入日志；不透明位置不提供 Debug 输出，也不进入界面或诊断。

旧数据库以事务迁移：保留账号 ID、凭据库引用、候选状态、UID 游标和信头重试；旧候选没有显式定位 JSON 时从原 UID 字段读取。
IMAP 连接限制保持不变，Outlook 地址只允许进入 API 账号语法校验，不绕过旧 IMAP 的 OAuthRequired 拒绝。

## 例子

用户同时连接 QQ 与未来的 Outlook 官方来源，两边发现“星河科技面试邀请”。QQ 用 UID 定位，Outlook 用自己的资源 ID 定位，但界面都展示发件人、标题、时间和筛选原因。
如果这封信已手动导入，扫描时跳过；如果发现后才手动导入，确认时跳过下载。
用户忽略的邮件再次扫描仍保持忽略。

API 第 2 页读取成功后，本机写盘失败：该页候选与下一位置一起回滚。
重启从第 1 页末的持久化位置重新读第 2 页，不跳过这页邮件。
如果下载过程中恢复了同一档案，恢复 epoch 已变化，旧下载结果被拒绝，不能直接写入恢复后的档案。
